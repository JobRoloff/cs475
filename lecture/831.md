## Background

Applying operations across matrix elements is fundamental to high-performance computing. Common examples include:

- LLM Tensor Parallelism: Splitting Query, Key, Value (QKV) matricies across multiple gpus where each gpu performs their own share of the computation and return a collective result. 
- Matrix Factorization: A technique used in PCA to identify __. This technique is also used in Recommender Systems to predict missing elements. 
- Eigenvector Computation: A computer vision technique for facial recognition

## Complexity & Scaling Challenges

Matrix element operations become performance bottlenecks due to two main factors:

1. The computation is heavy per cell (e.g., computing convergence depth a mandelbrot fractal)
2. The computation depends on the value of a neighboring or previously calculated cells

Because traversing an M x N matrix requires O(M x N) operations, execution time scales quadratically when M = N.

Shared memory parallelism (such as OpenMP) distributes loop iteracitons across execution threads to reduce total runtime.

## Questions to Ask Before Implementing OpenMP Parallelism

Consider theese critical areas:

1. Loop Indepencence & Data Dependencies
2. Variable Scoping & Lifetime
3. Shared State Accumulation & Synchronization
4. Work Load Balance & Loop Structure
5. Memory Access Patterns & Cache Behavior

**Loop Indepencence & Data Dependencies**

iterations are not independent if a cell from a different row / column is needed to preform the current cell's write operation.

if loop iterations can not run out of order, parallelizing without code refactor will produce race conditions

**Variable Scoping & Lifetime**

Variables declared inside the loop body is automatically thread private. (e.g., loop counters, temporary local accumulators or intermediate temporary variables).

Variables declared outside the loop defaultes to shared across all threads. These should be (e.g., read only, output buffers). Writes to shared variables must be synchronized

**Shared State Accumulation & Synchronization**

If threads write to a shared variable, use pragma:
- reduction(op:var)
- critical
- barrier
- atomic

reduction is good for updating ccaalar values. They give each thread a privary copy and safely merges results at the end

critical is good for non-atomic operations like collection update. Alternatively use a temporary thread local collection during the loop and merge them once post-loop.

atomic  is good for updating a single shared memory location(e.g., incrementing a global counter or modifying an array element) with minimal overhead comparee to critical.

barrier is good for enforcing an explicit checkpoint where all threads must wait until every thread reaches that point before proceeding (e.g., between dependent execution phases)

**Work Load Balance & Loop Structure**

Scheduling tasks amungst threads depend upon how balanced work is across the matrix. This is specified using the schedule() pragma

If work is evenly distributed across the matrix, use schedule(static)
else use either
- schedule(dynamic, chunk_size)
- schedule(guided)

parallelizing the outer loop by default maximizes thread work granularity and reduces thread creation / syncronization overhead

if the outer loop doesn't have many iterations, you can collapse the outpuer loop to expand the iteration space. this is done using the collapse(2) to increase parallel throughput.

**Memory Access Patterns & Cache Behavior**

When a CPU reads an array element from ram, a full 64 byte chunk is loaded into L1/L2 cache.

Storing matrix values in row-major order (matrix[row][col]) allows for element of the same row to be cached. This allows for the inner loop to hit the cache when traversing the stored matrix rather than needing to load new values into L1/L2 cache. If the data was stored via matrix[col][rox], every time the inner loop increments, there would be no cache hits since the CPU would need to re load new a 64 byte chunk.


If two threads write to different variable that share the same 64 byte cache line, the CPU cores fight over ownership of that cache block. This mean when one core write to an element, it envalidate the other core's cache line. This results in CPU core 2 to reload its cache line just becore CPU core 1 updated. This is prevented using 2 approaches:

1. Privatize: have each thread update a local variable inside the loop. From there, write to shared memory only once at the end.
2. Pad: Add meaningless padding bytes between thread-specific array elements so each thread's variable lands on a separate 64 byte boundary.


## Notes

- Threads can have their own copy of a variable if the variable is marked as "private"
    - the first element value can be initialized to that of the main thread if its marked as "first private"

## Examples

**Example 1**

```c
{
    x[0] = expensive();
    for (i=0; i < n; i++){
        for(j=1; j < 10; j++){
            x[j] = compute(x[j-1], i);
        }
        answer[i] = x[1] + x[9]
    }
}
```

What is a thought process for a openmp refactor?

Thought process:

1. Loop Indepencence & Data Dependencies
    a. (INDEPENDENT) i = 1 does not depend on i = 0
    b. (INDEPENDENT) each outer loop computes its own elemnts for x and writes to a collection where threads can write to it in any order (each outer loop has its own spot in the output array).
    c. (DEPENDENT) The inner loop has a strict dependency between its iterations of j.
2. Variable Scoping & Lifetime
    a. (RACE CONDITIONS && FALSE SHARING): the inner loop's operation on the shared x array will be problematic when the threads execute its inner loop. This will require privitixint the inner loop's copy of the x array
3. Shared State Accumulation & Synchronization
    a. since anser[i] writes to a distinct memory location for each i, no atomic operations or critical section is needed
4. Work Load Balance & Loop Structure
    a.  depending on the workload balance, we'd use diffenent schedule clause arguments.
5. Memory Access Patterns & Cache Behavior

solution: 

```c
{
    x[0] = expensive();
    #pragma omp parallel for firstprivate(x) schedule(static)
    for (i=0; i < n; i++){
        for(j=1; j < 10; j++){
            x[j] = compute(x[j-1], i);
        }
        answer[i] = x[1] + x[9]
    }
}
```

How might this be parallelized?

1. Loop Indepencence & Data Dependencies
    a. (INDEPENDENT) outer loop index value doesn't depend on the one before it
    a. (DEPENDENT) inner loop body relies on computed value from previous iteration 
2. Variable Scoping & Lifetime
    a. shared answer array is written to such that separate threads won't write to the same index
    b. loop counters stay private to each thread
    c. x array within each thread must be private to avoid threads over writing the same copy's intermediate values
    d. 
3. Shared State Accumulation & Synchronization
    a. 
4. Work Load Balance & Loop Structure
    a. 
5. Memory Access Patterns & Cache Behavior
    a. 


solution:

```c
{
    #pragma omp parallel for private(x) private(j) lastprivate(x)
    for (i=0; i < n; i++){
        x[0] = 1.0;
        for(j=1; j < 4; j++){
            x[j] = compute(x[j-1] * (i+1));
        }
        answer[i] = x[0] + x[1] +x[2] + x[3];
    }
    result = x[3]
}
```
